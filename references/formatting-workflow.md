# 排版工作流

目标不是“套模板”，而是让版式服务于文章的阅读路径。所有可发布内容必须遵守 [wechat-html-spec.md](wechat-html-spec.md)。

## 1. 先做内容诊断

在写 HTML 前，静默确定：

1. **读者与场景**：新手学习、专业决策、行业观察、情绪共鸣或行动转化。
2. **一个核心承诺**：读完后读者会理解、判断或完成什么。
3. **文章结构**：观点递进、教程步骤、数据比较、时间演变、案例复盘或新闻证据。
4. **信息密度**：文字应主导，还是需要一个比较/流程/时间线图来降低理解成本。
5. **语气**：克制、温暖、专业、紧急或实验性；选择一个主风格，不混搭成拼贴。

只把有助于理解的内容做成视觉组件。原文没有证据时，不用设计制造“已证实”的错觉。

## 2. 选择配方与构图

读 [style-recipes.md](style-recipes.md)，按内容而不是个人偏好选择一个配方。然后固定：一个中性色基底、一个主强调色、最多一个辅助提示色、一套圆角与边框语义。

- 首屏只解决“为什么值得读”：栏目/语境、标题、可选副标题或关键结论。避免大面积装饰图抢走标题。
- 每个大节用一致但不机械的节奏：节标题 → 解释段 → 证据/例子/图 → 小结或过渡。
- 通常每 300–500 字仅安排一个有信息价值的视觉停顿；一篇挑 3–5 类组件，深色整块不超过 3 个。
- 移动端正文控制在约 14–16px、1.75–1.9 行高，所有关键内容在单列内完成；不要依赖横向滚动或 `gap`。

## 3. 内容与组件映射

| 内容目的 | 优先组件 |
|---|---|
| 给出总判断 | Hero / 结论卡 / 金句引用 |
| 解释多步骤方法 | 编号节头 + 步骤卡 + 流程 SVG |
| 让读者比较选择 | 双栏对比卡或双卡 SVG |
| 呈现数据、趋势、时间 | 静态 SVG；只显示有来源的数据 |
| 给出经验、案例、访谈 | 引文、证据卡、前后对照 |
| 提醒边界与风险 | 低饱和 callout；警示色只用于真正的风险 |
| 收束和行动 | 3 条以内的清单或简短总结块 |

在 [components.md](components.md) 取片段，并将颜色替换为所选配方 token。不要为装饰而把每段文字包进卡片。

## 4. 图片与图表

优先级：

1. 数据、步骤、比较、时间线：静态内联 SVG。使用 `viewBox`，宽度 `100%`，无需互动。
2. 产品界面、研究证据、现场照片：用户素材或来源可信且可使用的真实图片；图片与紧邻论点对应，并写必要图注/来源。
3. 概念插画或封面：可以生成，但不可伪装成新闻现场、产品实拍或研究证据。
4. 没有可用图时：宁可保留留白和好排版，也不要编造链接或堆无关配图。

仅走复制粘贴时，base64 图片可作为交付方案。走 API 时，保留本地路径、真实 URL 或 data URI；脚本负责上传为微信 URL。正文图必须满足格式和 1 MB 限制。

## 5. 本地验收清单

交付/接入前检查：

- 标题、开头和每节小标题能脱离设计读懂；首屏有明确价值。
- 视觉层级来自字号、字重、留白和少量颜色，而非每段换背景。
- 没有连续的同款卡片墙；每个图、色块、标签都有语义。
- 手机窄屏无裁切、重叠、横向依赖或过长代码行。
- 正文标记区内没有预览壳的 `<style>`、`class`、`id`、按钮或脚本。
- 图表、数字、引用和图片来源没有被设计夸大；图片 URL 均真实可用。
- 若接入 API，再运行 CLI 预检并修复阻断项。
